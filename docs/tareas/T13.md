# T13 — API de verificación de correo y recuperación de contraseña

## Objetivo

Implementar los flujos de seguridad de cuenta: verificación de correo
electrónico (envío tras el registro y reenvío bajo demanda, más confirmación
por token), recuperación y restablecimiento de contraseña olvidada, y cambio de
contraseña desde una sesión activa.

## Qué hacer

1. **Módulo `CuentaModule`** (`apps/api/src/cuenta/cuenta.module.ts`):
   Implementa y exporta el servicio de verificación/cuenta para que `AuthModule`
   pueda inyectarlo en `AuthService`. `CuentaModule` ya está importado en `AppModule`.

2. **Tokens de un solo uso** (`tokens_verificacion`):
   - Token aleatorio de 32 bytes (`randomBytes(32).toString('base64url')`).
   - En `tokens_verificacion.tokenHash` se guarda únicamente su hash SHA-256 en
     hexadecimal; el token en claro solo viaja en el correo y nunca se escribe
     en la base de datos ni en los registros (`Logger`).
   - Vigencias: **24 horas** para `verificar_correo`; **1 hora** para `recuperar_contrasena`.
   - Al pedir un token nuevo para un `(usuarioId, tipo)`, invalida los tokens
     anteriores no usados del mismo usuario y tipo (por ejemplo marcando
     `usadoEn = ahora` o eliminándolos en la misma transacción).
   - Al consumir un token: verifica en transacción que exista por `tokenHash`
     y `tipo`, que `usadoEn IS NULL` y `expiraEn > ahora`, y márcalo `usadoEn = ahora`
     de forma atómica (condición `AND usado_en IS NULL` en el `UPDATE ... RETURNING`).

3. **Endpoints** (según `packages/contracts/src/cuenta.ts`):
   - `POST /auth/verificar-correo/enviar` (requiere sesión; 204):
     - Si el correo ya está verificado (`emailVerificadoEn !== null`), responde 204
       sin enviar correo innecesario (o documenta este comportamiento idempotente).
     - Si no, genera token `verificar_correo` (24 h) y envía correo con `Mailer`
       al enlace `${WEB_URL}/verificar?token=${token}`.
     - `@Throttle({ default: { limit: 5, ttl: hours(1) } })` o similar razonable.
   - `POST /publico/verificar-correo` (`@Publico()`, `@Throttle` estricto; 204):
     - Valida `verificarCorreoSchema`. Consume el token `verificar_correo` y
       actualiza `usuarios.emailVerificadoEn = ahora`.
     - Token inexistente, usado o vencido → `400 VALIDACION` o `404 NO_ENCONTRADO`
       / `409 CONFLICTO` con mensaje claro (sin revelar datos del usuario).
   - `POST /publico/recuperar` (`@Publico()`, `@Throttle` estricto, ej. 5/hora; 204):
     - Valida `solicitarRecuperacionSchema`.
     - **Siempre responde 204**, exista o no el correo (y aunque el usuario esté
       inactivo, no envíes correo pero responde 204 igual para evitar enumeración).
     - Si el usuario existe y está activo, genera token `recuperar_contrasena` (1 h)
       y envía correo con `${WEB_URL}/restablecer?token=${token}`.
   - `POST /publico/restablecer` (`@Publico()`, `@Throttle` estricto; 204):
     - Valida `restablecerContrasenaSchema`.
     - En una transacción: consume el token `recuperar_contrasena`, actualiza
       `usuarios.passwordHash` con Argon2id (`argon2.hash`), invalida los demás
       tokens de recuperación pendientes del usuario y **revoca todas las sesiones**
       activas del usuario (`sesiones.revocadaEn = ahora` donde `usado/revocadaEn IS NULL`).
   - `POST /auth/cambiar-contrasena` (requiere sesión; 204):
     - Valida `cambiarContrasenaSchema`.
     - Verifica `passwordActual` contra `usuarios.passwordHash` con `argon2.verify`.
       Si no coincide → `401 NO_AUTENTICADO` (o `403 SIN_PERMISO` / `400 VALIDACION`;
       no `500`).
     - En transacción: actualiza `passwordHash` con `argon2.hash(passwordNueva)`
       y **revoca todas las sesiones del usuario salvo la actual**
       (`sesiones.id <> sesion.sesionId` y `revocadaEn IS NULL`).

4. **Enganche en el registro (`apps/api/src/auth/auth.service.ts`)**:
   - Al final de `AuthService.registrar()`, después de crear empresa/usuario/miembro
     y sesión, llama al método exportado del servicio de `CuentaModule` para
     enviar el correo de verificación al usuario recién creado.
   - Si el envío de correo falla en desarrollo o en una prueba? No silencies
     errores inesperados salvo que esté justificado, pero recuerda que en
     `crearAppDePrueba()` `Mailer` es `MailerEnMemoria` y siempre resuelve.
   - Si `AuthModule` importa `CuentaModule`, evita dependencias circulares
     usando `argon2` directamente en `CuentaModule` (para no tener que importar
     `AuthModule` desde `CuentaModule`).

## Criterio de terminado

- Todos los endpoints cumplen `packages/contracts/src/cuenta.ts` y aparecen en `/api/docs`.
- El registro (`POST /auth/registro`) envía el correo de verificación y las pruebas existentes de `auth.int-spec.ts` siguen pasando en verde.
- Pruebas de integración en `apps/api/test/cuenta.int-spec.ts` que cubran:
  - envío y verificación de correo (token válido marca `emailVerificadoEn`, segundo uso falla, token expirado falla, token anterior invalidado al pedir uno nuevo);
  - recuperación de contraseña: `POST /publico/recuperar` responde `204` tanto para correo existente como inexistente (sin enviar correo en el segundo caso);
  - restablecer contraseña: cambia el hash, el usuario puede ingresar con la nueva contraseña, revoca todas sus sesiones activas y otros tokens de recuperación; token usado/vencido/inexistente falla;
  - cambiar contraseña: exige `passwordActual` correcta, cambia la contraseña, mantiene viva la sesión actual y revoca todas las demás sesiones del usuario;
  - verificar explícitamente que ningún token en claro aparece en `tokens_verificacion` (`tokenHash !== token` y coincide con `sha256(token)`) ni en los logs.
- Comentarios TSDoc según `AGENTS.md` §3 en controladores y servicios.
- Verificación de `AGENTS.md` §5 en verde (`pnpm format`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:int`, `pnpm build`).
